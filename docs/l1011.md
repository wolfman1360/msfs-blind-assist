# iniBuilds L-1011 TriStar

Aircraft code `INI_L1011`, menu item "iniBuilds L-1011 TriStar". Community package
`inibuilds-aircraft-l1011` (MSFS 2024 only; built and tested against package 1.0.8). Design
document: `docs/superpowers/specs/2026-10-02-l1011-tristar-design.md` (local, not in the repo).

Session 1 covers the switch panels, readouts, warning-light announcements, the Ctrl+M monitor
manager, the circuit-breaker window and the aircraft's own checklist; session 2 the glareshield
autopilot (AFCS); session 3 the three INS units, the two PMS units and the INS window; session 4
the Paper Flight Bag tablet.

## How a control is written

The TriStar's cockpit gauges re-read a switch only when the H: events its click code fires
arrive. Writing the switch's L:var alone moves the 3D switch and changes nothing else; so does
`SetLVar`'s data-definition write. So every write of a map-driven panel row or a circuit breaker
REPLAYS THE COCKPIT'S OWN CLICK: the L:var writes, H: events and K: events the control's mouse
code performs for the chosen position, in order, as one calculator-path string
(`L1011WritePlan`), sent with `ExecuteCalculatorCodeUnique` so a repeated press is never
coalesced. A string longer than 900 characters is split at effect boundaries (MobiFlight's
command limit is 1024 bytes).

The deliberate exception is the hand-written rows in `L1011Levers`, whose controls the map does
not cover well. They write what the aircraft itself reads rather than replaying a click: the flap
handle writes `A:FLAPS HANDLE INDEX` (as the aircraft's own EFB does); the gear lever goes down
and up through the stock `K:GEAR_DOWN` and `K:GEAR_UP`, which the HANDLING gauge intercepts, and
to Off by writing `L:LEVER_LANDING_GEAR` 50, which that gauge polls; the speed brake writes
`L:LEVER_SPOILERS`, which the HANDLING gauge copies into the stock handle; the ground-spoiler arm
and the parking brake send `K:SPOILERS_ARM_SET` and `K:PARKING_BRAKE_SET`; the typed altimeters,
frequencies and squawk send the stock set events. Each is still one `ExecuteCalculatorCodeUnique`
string, refused aloud when the calculator path cannot land, and never `SetLVar`.

Input mode adds two keys for the same typed values. Ctrl+B opens the shared `ValueInputForm` and
sets all three altimeters (captain, first officer, standby) from one entry, with the typed
altimeter fields' range and error; the three `K:2:KOHLSMAN_SET` writes go as one string
(`L1011Levers.AllAltimetersRpn`) and the pilot hears "Altimeters 1013, 29.92". No STD or units
button: the altimeters are steam gauges. Ctrl+N opens the shared `NavRadiosForm` and sends NAV 1's
and NAV 2's frequency (`K:NAVn_RADIO_SET_HZ`) and course as one string
(`L1011Levers.NavRadiosRpn`); the course goes through `K:VOR1_SET` / `K:VOR2_SET`, which is what
the course knobs' INSTRUMENTS script sends, and lands in `A:NAV OBS:1/2`. It confirms "NAV 1
110.30, course 45; NAV 2 113.90, course 270". The NAV dialog is pre-filled through
`SimConnectManager.RequestNavRadioInfo`, the fixed one-shot read every aircraft's N readout uses
(no new definition), or 108.00 and course 0 when that does not answer within 2 s. Both keys are
refused aloud ("Altimeters unavailable", "NAV radios unavailable") when the calculator path
cannot land, before the dialog opens and again when a value is set. Both dialogs are tracked
windows, so an aircraft switch closes them.

- Buttons: press, hold, release. The hold is 250 ms when the press fires an event and 2 s when it
  only writes an L:var a gauge polls (test buttons, APU start), so the poll cannot miss it. The
  APU start press also sends `H:APU` after the switch, as the tablet's APU ON step does: the
  switch alone cycled the inlet doors and the APU never turned ([L1011-22]).
- The autopilot engage paddles stop at CWS on the way from Off to Command ([L1011-21], see
  "How the autopilot engages").
- Latches (the electrical CLOSE/TRIP buttons): press only; the aircraft resets them.
- Spring switches (fire bottle discharge): the chosen side, held 1.5 s, then back to centre.
- Knobs (dimmers, temperature): a slider; the value goes into the knob's own set template. A knob
  is read on request (when its panel opens), never by the batch, so its cache can be stale: a knob
  write is skipped as already there only when MSFSBA itself has just commanded that value, and the
  knob is read again after each write (below), so the slider and the next write follow the aircraft.
- Encoders (knobs that only turn): an "increase" and a "decrease" button.
- A transition that carries a TOGGLE K: event (fuel cutoff valves and a few others) is refused
  while the current position is unknown, because a toggle sent the wrong way inverts the switch.
  The pilot hears "position unknown, try again in a moment".
- What MSFSBA has just commanded is remembered for 2.5 s (`L1011CommandedState`), so two quick
  picks are not both planned from the 1 Hz cache.
- Every write is refused aloud ("{name} unavailable") when `SimConnectManager.CalcWriteCanLand`
  is false, and the row's value is asked for again so its combo goes back to the position the
  aircraft is in (the levers included). The TriStar registers `MSFSBA_BRIDGE_PROBE`, so a missing
  MobiFlight WASM module is reported by the calc-path probe's spoken warning.
- Every Set write (a switch, a selector, a knob) is read again once it has landed, 1.5 s after its
  plan has run, a spring switch's return included (`L1011WritePlan.ReReadSettleMs`, one batch
  period plus margin: a judgement, not a measurement), so the combo or slider shows what the
  aircraft did. A gauge can put a switch straight back without the variable ever changing (the
  ground service bus picked to APU or External power returns to Off), and then no delivery would
  come to correct the combo. Only the last write of a burst to one row is read again: a slider swept
  by a held key writes every step, and an earlier step's answer would pull the thumb, and the next
  write, back behind where the pilot has got to.
- The gear lever's own gauge refuses "up" on the ground: the write lands and nothing moves. So
  after a gear-lever write the lever is read again once, 1.5 s later (`L1011Levers.GearSettleMs`,
  the same settle as a Set write's), and the combo follows what the aircraft did.

## The generated control map

`MSFSBlindAssist/Resources/l1011_control_map.json` is GENERATED by `tools/l1011-gen` from the
aircraft's two compiled cockpit behaviour files and its `en-US.locPak` tooltips, and shipped as
an embedded resource. Never hand-edit it. After an iniBuilds update:

```bash
git show HEAD:MSFSBlindAssist/Resources/l1011_control_map.json > old_l1011_map.json
```

```bash
python tools/l1011-gen/generate_l1011_map.py --package "D:\games\MSFS2024\Community2024\inibuilds-aircraft-l1011"
```

```bash
python tools/l1011-gen/diff_maps.py old_l1011_map.json MSFSBlindAssist/Resources/l1011_control_map.json
```

Then build and run the tests: `L1011PanelLayoutTests` fails if a layout row names a control the
new map lost. The checklist is regenerated the same way with `convert_checklist.py`.

Package 1.0.8 gives 778 controls (407 switches, 187 buttons, 67 knobs, 47 encoders, 22 latches,
4 spring switches, 44 the map cannot replay), 981 circuit breakers and 496 lamp variables.

## Panels

`Aircraft/L1011/L1011PanelLayout.cs` and its row files (`L1011LayoutRows.*.cs`) are the ONLY source
of panel order: the manual's flows (cockpit safety inspection, flight engineer station preparation,
overhead, main panel, center console). Spoken names put the discriminator first
("Tank 2 left pump 1"), and a row's position words override iniBuilds' tooltip words only where
the aircraft has none, a wrong one, or two the same. The levers, typed values and the breaker
button are hand-written in `L1011Levers`.

iniBuilds' tooltip words are upper case. `L1011PanelLayout.SpokenWord` puts them in sentence case
("ALTITUDE MODE ON" becomes "Altitude mode on") but keeps a single letter ("Loop A", "System B"),
a word with a digit ("1A", "N1") and the abbreviations pilots say as letters (APU, DC, RA, TA:
"TA/RA", "APU generator", "Standby DC bus") in capitals. That list was taken from the words of
the rows the layout places; add to it when a later session places a row with another one (the
map's unplaced AFCS and INS controls carry CWS and INS).

`SWITCH_APU_AUTOFIRE` (APU auto fire shutdown) stops the APU and closes fuel valves 8 and 9 on
EITHER click, on or off: that is iniBuilds' own click code, replayed faithfully. Moving it with
the APU running shuts the APU down.

Two rows are named against iniBuilds' tooltips: the weather radar's OFF and TEST buttons. Their
tooltips are swapped; the gauge (H:SWITCH_WX_OFF selects the OFF mode, `L:WX_Mode` 2) and the
variable ids agree with each other, so the rows follow them.

The status displays read what the cockpit gauges read (`L1011Readouts`): the engines' own EPR, N1,
N2 and N3 variables, hydraulic systems A to D from their pressure checkers (systems.cfg actuators 7 to
10), the AC and essential buses by index, the generator fields and breakers and the AC tie
breakers from their relays (their CLOSE and TRIP buttons are latches the aircraft resets), the
ALT SEL knob's cabin altitude (`L:TARGET_CABIN_ALTITUDE`), the BARO SET knob (Kohlsman 4), the
cabin barometric setting (Kohlsman 5) and the outflow valves; each pilot's decision height and
reference speed bug; each INS's distance and time to its waypoint; the zone set, zone and pack
temperatures; and the bleed and pack valve flowbars and wing anti-ice valves as on/off and
open/closed. A zone line says "zone" and a flowbar "valve flow", so neither takes the name of the
knob or switch beside it.
Two cockpit indications are not read: the start duct pressure and the engine anti-ice valve
lights. Both come from named pneumatic components (`PNEUMATICS COMPONENT PRESSURE:'Junction_1'_n`,
`PNEUMATICS VALVE STATUS:'Valve_1'_n`), which a calculator string reads (66 psi live) but a
SimConnect data definition cannot name: by number the same variable reads 0. The starter still
cuts out by itself (L1011_OVERHEAD_PANEL.js: N2 above 55 percent or duct pressure below 25 psi),
and N3, the manual's start cue, is read. The stabilizer trim readout is the tablet's takeoff "STAB
TRIM" scale (0 to 10 degrees nose up; the Autocomplete's `ELEVATOR_TRIM_SET` 4000 read 2.44), and
the "Stabilizer trim" row beside the flap handle sets it the same way.

## Budget

Switch positions, the announced levers, the warning lights, the autopilot's armed and captured
flags and alpha mode, each INS's alignment status and the PMS flight phase ride the continuous
batches (510 batch slots; no individual data definitions); readouts, knobs and the autopilot's two
inner-loop variables are on-request (196 definitions); buttons and typed entries are never registered. `IniL1011DefinitionTests` caps the
batch at 900 and on-request definitions at 300, leaving room for the later sessions. A position
variable two rows share rides the batch once.

## Announcements and Ctrl+M

- Positions are consumed silently in `ProcessSimVarUpdate`; the open combo follows them
  (`RefreshControlWhenDefHandled`).
- Warning lights (`L1011Annunciators`) speak through `L1011LampGate`: a silent baseline, a 1.2 s
  settle (a flashing lamp is heard once, in the state it settles in) and silence while either
  annunciator light-test switch is on and for 3 s after. They are spoken from
  `OnContinuousBatchDelivered`, outside MainForm's mute wrap, so the flush checks
  `L1011DisabledMonitorVariablesSet` itself. Besides the warnings and cautions they include the
  engine start valve open lights, the APU's doors in transit, battery condition, inlet flow, max mode
  and fuel lights, the IDG low pressure lights, the standby power flowbar, the four jettison dump
  lights, the autobrake armed light, the refuel power on light and the captain's engine 2 fail light.
- The flap handle, parking brake and ground-spoiler arm speak when something other than MSFSBA
  moves them, from `ProcessSimVarUpdate`, where MainForm's wrap applies the Ctrl+M mute and the
  UI echo (`DefAnnounceMuteSets` lists `INI_L1011`).
- A context reset (disconnect, flight load) wipes every baseline; the MD-11's `Md11SeedGate`
  decides from the batch deliveries when the lamps and levers a load left unchanged are seeded
  from the cache.

## Circuit breakers

981 breakers (numbered 1 to 999; 644 named) are never data definitions. The breaker window reads
them all with one Coherent debugger evaluation in the hidden `L1011_ENGINEER_PANEL` view
(`L1011CircuitBreakers.BulkReadScript`), and pulls or pushes one by replaying its click.

- Every row carries its number: "ENG START PWR, breaker 741: in", and "Breaker 12: in" for the
  ones iniBuilds left unnamed. 68 breakers are titled "INOP" and three titles appear twice (ENG
  START PWR 741 and 921, INS-1 DC 787 and 804, AUDIO CONT F/O & OBS 541 and 927), so without it
  rows read the same; the search matches the number too.
- The list is re-filtered only when the window opens, the search or "Show pulled breakers only"
  changes, or Refresh is pressed. A pull or push, and the confirmation read 1.5 s later, rewrite
  the listed rows in place without adding or removing one (`L1011CircuitBreakers.ItemTexts`), so
  the cursor never moves to another breaker; a breaker pushed in while "pulled only" is ticked
  stays listed until the list is next re-filtered.
- A screen reader does not read a row again when its text changes under a steady focus, so the
  confirmation read speaks the result once (`L1011CircuitBreakers.Confirmation`): "INSTR GND
  COOL, breaker 285: pulled", or "INSTR GND COOL, breaker 285: still in" when it did not move.
- Every open starts clean, as the Ctrl+M monitor managers do: the search empty and "pulled only"
  unticked (`L1011CircuitBreakerForm.PrepareToShow`), so the window never opens on a short list
  for a reason the pilot cannot hear.
- A pull or push before the states have been read is refused: "Breaker states unknown. Press
  Refresh." Nothing is sent, because which way the click goes is unknown.

## Autopilot (AFCS)

The glareshield panel is the "Autopilot" panel, first in the Main Panel section
(`L1011LayoutRows.Autopilot.cs`). Its first rows follow the manual's main-panel preparation item by
item (HSI sources; speed V2+70; heading set and HDG; flight directors on; autopilots off; both
courses; altitude set and armed; TO/GA), then the rest of the glareshield left to right, then the
two AFCS warning panels' ALERT reset buttons. The switches, mode buttons, ALERT buttons and the
captain's yoke TOGA button are map rows; the six typed values and the disconnect button are
hand-written keys (`L1011Afcs`). The typed values are written EXACTLY as the aircraft's own knob
handlers write them (L1011_AFCS.js / L1011_INSTRUMENTS.js, package 1.0.8), so a typed value lands
where a knob turn would have put it:

- heading `K:HEADING_BUG_SET` (window: `AUTOPILOT HEADING LOCK DIR`), courses `K:VOR1_SET` /
  `K:VOR2_SET` (windows: `NAV OBS:1/2`);
- altitude `L:ALTITUDE_SETPOINT_0` then `H:AUTOPILOT_CAPTURE_UPDATE` (0 to 50,000, 100 ft steps);
- speed `L:INI_AT_TARGET` (100 to 350 knots; the knob's clamp);
- vertical speed `L:INI_VS_PID_SETPOINT_2` then `H:AUTOPILOT_SWITCH_AFCS_VS_SEL` (100 fpm steps).

Live at a KLAS gate (2026-10-03, ground power): heading 090, speed 250, altitude 35000 and
courses 247/067 each appeared in their windows; vertical speed -1500 read "-X1500" once VS mode
was on. The speed window does not always show `INI_AT_TARGET`: with thrust management engaged it
shows an EPR target, or the PMS phase speed (250/320 knots, Mach .82/.83/.80) — the gauge's own
logic.

Two aircraft rules the app enforces up front, because otherwise a press is silently undone:

- Every pitch and lateral mode button (`L1011AfcsModes.NeedFlightDirectorOrAutopilot`) is turned
  straight back off by L1011_INS.js while `L:AUTOPILOT_ACTIVE_MODE` is 0 and both flight
  directors are off (seen live). When MSFSBA KNOWS both flight directors are off and both engage
  switches are at Off, the press is refused aloud ("turn on a flight director or the autopilot
  first"); an unknown position never refuses.
- Turning vertical speed mode on sets the target to the current vertical speed rounded to 100
  (seen live: a -1500 typed beforehand read 0 afterwards). So the Ctrl+V box is read-only while
  the mode is known to be off, as the PMDG 737's V/S box is until V/S is engaged
  (`AfcsBoxTakesTyping`), and a vertical speed typed on the panel while the mode is known to be
  off is refused aloud ("turn vertical speed mode on first").

Thrust management is turned straight back off by the INS gauge unless an autopilot is master and
the PMS has an EPR (its takeoff page SAT entry or the climb page) or the phase is cruise
(instruments reference, not measured live); the value box's read-back says so ("Thrust management
off").

The disconnect button fires `H:AUTOPILOT_AUTOPILOT_DISCONNECT`, the one event the yoke switch's
click fires in either direction and the event the aircraft turns the stock `AUTOPILOT_OFF` key
into (L1011_HANDLING.js). Live: with autopilot A in Command (`L:AUTOPILOT_ACTIVE_MODE` 2), it set
the engage switch to Off, the active mode to 0, and pulsed `L:autopilot_disconnect`. The TOGA
button replays the yoke's press (`L:YOKE_CPT_TOGA_PUSH` and `H:YOKE_CPT_TOGA`); the compiled
systems module reads it, and at the gate it changed nothing visible — check it on a go-around.

What speaks (`L1011AfcsModes`, through `L1011AfcsAnnouncer`, baseline-first, from
`ProcessSimVarUpdate` under MainForm's mute wrap): the engage switches (Command/CWS/Off), the
two-position switches and mode buttons, and eight flags the gauges drive as they arm and capture
— `ANN_LOC_ARM`, `ANN_LOC_ACTIVE`, `ANN_VOR_ACTIVE` (the INS gauge's; it counts only while VOR or
back course is on, because the gauge sets it whenever a navaid is received with no localizer, ILS or
back-course mode on: [L1011-12]), `ANN_ILS_ARM` (glideslope armed), `ANN_ILS_ACTIVE` (glideslope captured), `ANN_ALT_ARM`,
`FLARE_ACTIVE`, `ROLLOUT_ACTIVE` (spoken only when they come on; `FLARE_ACTIVE` reads 99 while
armed, which is not spoken; the status display reads it "armed"). The autothrottle's alpha mode,
`L:INI_AOA_SPEED_MODE` (Ctrl+P's "Speed: AOA"), speaks both ways, "Autothrottle alpha mode" and
"Autothrottle alpha mode off", with its own Ctrl+M row; it is never MSFSBA's press, so it always
speaks. MSFSBA's own press is silent
while the switch sits where it was put — the PMDG windows' value-matched echo — and any other
movement within `L1011CommandedState.HoldMs` is the aircraft's and is spoken; a value box button
or toggle key speaks its own read-back instead, once. There are NO autopilot-disconnect or
autothrottle-disconnect warning-light variables in package 1.0.8 (the gauge drives `AFCS_CPT_*`
0/50/100 annunciator values whose legends are a texture detail the code does not name), so a
disconnect is heard as the engage switches' change. The glareshield ALERT lights
(`CPT_ALERT_ILLUM`, `FO_ALERT_ILLUM`) and `LX_MIP_DUAL_AVL` are not announced: their meaning is
not documented and could not be confirmed. The ALERT reset buttons are on the panel.

### How the autopilot engages

L1011_INS.js on INS 1's gauge runs the whole autopilot. Its outer controllers (vertical speed,
altitude, heading, INS, VNAV, IAS and Mach) each publish a setpoint, `L:INI_PITCH_MASTER` and
`L:INI_ROLL_MASTER` pick which setpoint is flown, and the inner pitch and roll loops fly it only
while `L:INI_PITCH_PID_STATE` and `L:INI_ROLL_PID_STATE` are 1. On any `AUTOPILOT_*` event the
gauge sets `L:AUTOPILOT_ACTIVE_MODE` from the two paddles (2 when either is at Command, 1 when
either is at CWS, else 0), and 50 ms later runs that paddle's routine for the mode:

- Off (mode 0) turns both loops off.
- CWS (mode 1) turns both loops on and holds the attitude the aircraft has.
- Command (mode 2) re-fires the selected mode buttons' events and leaves the loops as they are.

So the Command light and `ACTIVE_MODE` 2 say only where the paddle is: a paddle sent straight from
Off to Command shows Command with both loops off, and the aircraft flies nothing. The cockpit
paddle cannot skip the CWS notch, so MSFSBA stops there too: a paddle going to Command from Off,
or from a position not known, goes to CWS, rests `L1011WritePlan.PaddleNotchMs` (500 ms) and then
goes to Command ([L1011-21]). Both moves in one string, or back to back, ran only the Command
routine, because the gauge reads the paddles 50 ms after the event; the rest outlasts that at 10
frames a second. The CWS notch is MSFSBA's own move (`L1011Plan.Via`), so it is not spoken.
TO/GA in flight and the gauge's own `AUTOPILOT_CONNECT` event also turn the loops on.

### Autoflight windows

The input-mode windows follow the A300's autoflight windows (on `feat/inibuilds-a300`):
`L1011AutoflightWindows` says what each carries, each control in one window only, labelled with
its panel row's name, and every press goes through the row's write path, so the refusals
("unavailable", "position unknown", the flight-director rule) and the commanded-position hold
match the panels. A button's label, a combo and a status line show the position the aircraft
reports, never the one just asked for (the PMDG windows' rule); the commanded position decides
only which way a toggle goes and whether a refusal applies.

- **Ctrl+S, Ctrl+H, Ctrl+A and Ctrl+V** open the value box for that axis: Speed with Thrust
  management, IAS hold and Mach hold; Heading with Heading and INS (Alt+N); Altitude with Altitude
  hold (Alt+H, the PMDG 737 altitude dialog's letter) and VNAV; Vertical speed with its mode
  button. A button press reads its
  result back fresh after `ToggleReadBackMs`, queued behind any call-out the press set off (the
  box's own echo reads the 1 Hz cache and is off).
  Every value box is one `ValueInputForm` type, so `ShowValueBox` closes an open box with another
  title first; Ctrl+B's altimeter box shares the slot.
- **Ctrl+P** opens the shared autopilot window (`PMDGAutopilotWindow`, the A300's) on a status
  list (`L1011AutopilotStatus`): the six glareshield windows exactly as drawn, the engaged modes,
  the armed and captured modes, the autothrottle, thrust management and both autopilots. Then the
  two engage paddles as combos, where the PMDG 737 has CMD A and CMD B (the shared window's
  `selectorsFirst`, which the PMDG and A300 windows leave off); Flight director A and B,
  Turbulence, ILS, Localizer, VOR, Back course and Autothrottle (Alt+T, where the 737 has its A/T
  Arm and the A300 its autothrottle button); and the one-shot Autopilot disconnect, captain's
  autothrottle disconnect and TOGA, which have no state. Nothing is spoken on a press; refusals
  are. Each button has its Alt key (Alt+D the disconnect, Alt+G TOGA); as in the PMDG windows,
  with focus on a button the letter alone presses it too.
- **Toggle keys**: Shift+A and Ctrl+O move autopilot A or B between Off and Command (from CWS to
  Off; from Off through CWS, as above), Ctrl+J the autothrottle, Ctrl+L the localizer, Shift+P the
  ILS; each reads its result back. With no approach mode on, the aircraft keeps one autopilot in Command: engaging the other
  moves the first to Off, and that change is spoken ("Autopilot A off", then "Autopilot B command").
  The autothrottle's read-back adds the target `L:INI_AT_TARGET` holds, read fresh ("Autothrottle on,
  speed 250"): the aircraft resets it to 250 when the autothrottle engages.
  An engage to Command reads `L:INI_PITCH_PID_STATE` and `L:INI_ROLL_PID_STATE` fresh after the
  paddle and names a loop at 0 ("Autopilot A command, not flying pitch", "not flying roll", "not
  flying pitch or roll"): a statement, never a refusal, so the press stands. Ctrl+P stays silent on a
  press ([L1011-11]): its Alt+T and paddle combos have no read-back, and its first list shows the
  speed window.
- **Output mode** Shift+H, S, A and V read the targets fresh.

The window's lines come from the Coherent debugger: `coherent-l1011-afcs-agent.js` in the
`L1011_AFCS` view returns `#screen_1..8` as drawn plus `#customElectricity`'s power state, and
`L1011AfcsWindows` turns them into lines ("Speed: IAS 250", "Pitch: VS -1500"). The gauge pads
blank digits with "X" (its font draws nothing); those are dropped. The panel is powered from the
`AFCS_PANEL` circuit (dark on battery alone; on with ground power). The shared window hides on
close and is reused, so the reader follows its `Visible`: it holds the view's one inspector socket
only while the window is shown, and forgets what it read when it stops; rows from a reader that
has been stopped are ignored, and reader errors go to the debug log.

### Capturing a display fixture

`tools/l1011-display-test` replays the in-page readers against live captures of their Coherent
views (`fixtures/`). To capture one, evaluate `tools/l1011-display-test/stamp.js` in the view; it
stamps `data-vis="1"` on visible elements and `data-rect` on all of them, returns the body's HTML
and removes the stamps from the live page. From `tools/`:

```powershell
./coherent.ps1 eval -Title L1011_AFCS -ExprFile l1011-display-test/stamp.js
./coherent.ps1 eval -Title L1011_INS_1 -ExprFile l1011-display-test/stamp.js
```

Save what it prints, without the first `# resolved` line, as UTF-8 under `fixtures/`. Close the
INS window first: the view takes one inspector socket.

The INS fixtures are `ins1-pos.html` and `ins1-status.html` (INS 1 navigating on the POSITION and
DESIRED TRACK/STATUS pages) and `ins3.html` (INS 3 aligned). Each was then trimmed of the digit
pictures that were not shown (`img.digit-layer` without `active`: 19 per digit, about 40 KB per
view, and the reader reads the spans); the picture that was shown stays. The lamps, selectors and
page globals are not in a capture; each test supplies them.

The tablet fixtures (`efb-*.html`) come from `efb-capture.js` instead, never `stamp.js`
([L1011-20]). It stamps the same visibility, keeps only the page shown (on the Menu, only the pane
shown) and removes inline handlers, decorative images, coordinates, field values, the Navigraph
sign-in code and user name, the airport shortcuts, the METAR answer and the OFP text (a two-line
stand-in), so no SimBrief ID, flight plan, airport or account is committed. The tablet client keeps
its view's socket until the aircraft changes, so switch aircraft or close MSFSBA first:

```powershell
./coherent.ps1 eval -Title iniEFBL1011_1 -ExprFile l1011-display-test/efb-capture.js
```

`efb-flows.html` was then trimmed by hand to its first three flows.

## INS and PMS

The Center Console opens with five panels: INS 1, INS 2 and INS 3 (each: the button that opens the
INS window on that unit, then its display selector, waypoint thumbwheel and AUTO/MAN/RMT selector)
and Captain PMS and First Officer PMS (the window button). The overhead mode selectors (MSU) stay
in the Overhead's "INS Mode Selectors" panel, where they read Off, Standby, Align, Nav and Attitude
(the aircraft's own labels are "Off, Stby, Align, Nav, Att"): the words the window's "Mode selector"
line says. The keypads are in the window, not on the panels.

The window (`Forms/L1011/L1011InsForm`, input-mode Shift+M) follows the fleet's CDU windows (the
A300 MCDU window, on `feat/inibuilds-a300`, the MD-11 MCDU window, the PMDG CDUs): MainForm owns
one window, hidden on close and reused;
the display comes first, then the input box, the unit combo and the unit's buttons. Every time it
is shown it opens on the display, also after Escape from the input box (the display is made the
active control before the window is shown, so the activation never restores the box; the first
activation after a show is held to the display too, `L1011InsShowFocus`). It shows one unit at a time. Its display is read through the Coherent debugger by the read-only
`coherent-l1011-ins-agent.js`, from the unit's own view: `L1011_INS_1` holds INS 1 and the
captain's PMS, `L1011_INS_2` INS 2 and the first officer's PMS, `L1011_INS_3` INS 3 (its PMS copy
is inert and never read). The reader holds only the shown view's socket and only while the window
is visible; a unit switch to another view moves it once the unit combo has rested for 300 ms
([L1011-13]). What the agent reads, and why (L1011_INS.js, package 1.0.8):

- The display windows are one-character hidden spans (`#left_0..5`, `#right_0..6`, `#tk_0..1`).
  The spans are written at once; the digit pictures beside them lag up to 200 ms, so the spans are
  the truth. A blank slot keeps its place.
- `#dot_5` is the left window's decimal point and `#dot_6` the right's; the other dots are
  degree/minute ticks. The dots cannot identify the page: the page is `L:INS_n_ROTARY_MODE`.
- There are no lamp elements: every lamp is an L:var (`INS_n_READY`, `_ALERT_INDEX`, `_WARN`,
  `_ON_BAT`, `_HOLD_LIGHT`, `_INSERT_LIGHT`, `_TK_CHG_LIGHT`, `_TEST`; the PMS mode lights
  `INI_CPT_PMS_*` / `INI_FO_PMS_*` and `PMS_n_INSERT_LIGHT`).
- An open entry (`isInput`, `isInputRight`, `isTrackChangeInput`), the PMS page state
  (`pms_is_input`, `pms_line_active`) and the nine waypoint slots (`gpsPoints[1..9]`, with
  `active_batch` / `batch_count`) are the gauge's own page globals, read by name behind `typeof`.
  The waypoint list never reads the `INS_WAYPOINTS` DataStore table: the gauge rewrites it only
  once a second and only while the unit has power.

`L1011InsScrape` reads the agent's rows back; `L1011InsDisplay` and `L1011PmsDisplay` write the
lines (one per braille line, updated in place): "INS 1: navigating", "Mode selector: nav",
"Display selector: position", "Present position: N 36 05.1, W 115 08.0", "Leg: 0 to 1", "Lights:
ready to navigate"; "Captain PMS, page: TAKEOFF", "1: GMT 0755Z", "2: EPR blank", "Lights: climb".
The gauge's "_" padding reads as one space and its "---" as "blank". A window whose digits are
separated by a blank holds no number and reads "no data": a unit just powered, with its display
selector not yet turned, still shows the gauge's power-up text "00000N" and "072  0 ", which read as
720 knots, 72.0 minutes or a status of 0720 before this rule (blanks before and after a number, and
after a side letter as in "R 0123 ", are padding). The "Mode selector" line is
the overhead MSU as the aircraft reports it (`L:ROTARY_INS_MODE_n`, read through its Overhead row,
not the INS view): off, standby, align, nav or attitude, so "All INS NAV" can be confirmed from the
window. In Attitude the unit's display is dark although the unit is on, so the window says "INS 1:
attitude mode" there, not "off". An open entry on the cross track page keeps the decimal point the
gauge draws: "Entry, left window: R 5.0" for a right 5 nm offset.

The display test (display selector at Test) shows every segment lit, "Leg: test pattern" and the
lights insert, track change and test: in this aircraft the test lights TK CHG, INSERT and TEST, not
HOLD (the cockpit's HOLD lamp is `INS_n_HOLD_LIGHT`, position hold; `INS_n_KEY_HOLD_LIGHT` is a
gauge variable with no cockpit lamp, so the window does not read it). Leaving Test, INSERT goes out
at once while TK CHG and TEST stay lit and the leg window keeps "88" until Desired track and status
is selected; on the position page trust the Entry line, not the insert light.

Keys: every key is the cockpit's own click on a map control (`L1011InsKeys`, `L1011InsDevices`):
the control's press effects, then its release effects (`L1011WritePlan.ForPress`). The INS takes
several keys in ONE calculator string with each key's press and release back to back and no delay
(measured live, 2026-10-15: "N" then "4 3 4" in one string read "  434N", and "0 9 INSERT" in one
string stored the latitude exactly as key by key), so a run of keys (typed text, one key, the
present-position sequence, INSERT; the PMS keys follow the same path) is sent as one
`ExecuteCalculatorCodeUnique` string, then a 50 ms pause (`L1011InsKeys.RunGapMs`) before whatever
is chained next. A run past 900 characters (`L1011InsKeys.MaxRunLength`; the MobiFlight command
channel holds 1,024 with the unique prefix) is cut into consecutive strings between keys, never
inside one, each followed by that pause. Everything goes through ONE chain in the definition so two
quick presses never interleave, and a selector move from the window waits behind every key already
chained ([L1011-14]); it took 60 ms of hold and 40 ms of gap per key before, about 1.5 s for a
position. The INS has no letter keys: N, S, E, W are the 2, 8, 6, 4
keys and L, R the 7, 9 keys. Typed text with a character the unit has no key for sends nothing at
all, says which keys exist and stays in the input box. Enter in the input box sends the keys;
Ctrl+Enter presses INSERT (the PMDG windows' Ctrl+Enter is EXEC). On a PMS, Ctrl+1 to Ctrl+6 (F1
to F6 with the alternate layout in FMC Settings) press the line keys, whose buttons name their line
and shortcut as the PMDG CDU window's buttons do ("Line 1, GMT (Ctrl+1)": the label words only, since
a value changes every second). Page Up and Page Down (and Alt+Up and Alt+Down as in the PMDG CDU
window, Alt+Left and Alt+Right as in the MD-11's, or Right Arrow on the display) change page; an INS's pages are its display selector's positions, so on an INS they turn
the selector one position through its row (`L1011InsPages`), stop at both ends ("Last position:
Test"), and say the new position once the aircraft reports it. Backspace on the display is CLR (CLEAR
on an INS). What was typed is read back once the keys have landed, as the fleet's CDU windows
read their scratchpad (`CduScratchpadAnnouncer`, fed with `L1011InsDevices.EntryLine`): the entry
as the unit shows it ("Entry, left window: 36051N", "1: GMT, entering: 1200Z"), or "Entry closed"
when the entry closes. On a PMS an entry that closes on its own page reads back what was stored
instead, then any other line the unit recomputed from it, leaving out the lines that move by
themselves (GMT, PR ALT, the climb page's SAT and TAS): "6: SAT 19. 2: EPR 1.632"
(`L1011InsDevices.InsertReadback`). That is a typed-value confirmation, so it speaks even with the
"entry closed" row muted. An INS's leg line and its leg call-out name the TO waypoint when it is an
imported fix ("Leg: 2 to 3, TANGI"). On a PMS, Clear deletes the last character and the entry stays open (Page
Up or Page Down abandons it); on an INS, Clear closes a position or waypoint entry and does nothing
on the cross track page (Insert or a selector move ends an offset entry). A PMS value the unit
refuses shows the gauge's ERROR word in its cell for about a second (on the cruise and descent
pages, "---" inside the label) and is read back as soon as it is seen
(`L1011InsDevices.EntryReadsAtOnce`); an INS INSERT the unit refuses (too few digits) changes
nothing on the display, so nothing is said and the entry line stays.

The TAKEOFF page wants its GMT first, as the manual's PMS preflight lists it: until a unit's GMT has
been inserted once, L1011_INS.js draws EPR, GW, FUEL and SAT as "---" whatever is typed
(`pms_gmt_initialized_ever`). The keys still land (the gauge's scratchpad held them, read over the
Coherent debugger) and the read-back says "4: GW, entering: blank", which is the aircraft, not the
window: insert the GMT on line 1, then the rest. Each PMS unit keeps its own GMT, so the first
officer's needs its own.

"Enter present position" turns the display selector to POSITION when it is elsewhere (the N/S/E/W
keys start no entry on another page), waits 400 ms (`SelectorSettleMs`) for the page to draw, then
types the simulator's latitude, INSERT, longitude, INSERT (15 keys, 744 characters: one string, so
the whole entry is chained for 450 ms with the move, 50 ms without it). Whether the selector must move
is decided when the run's turn comes in the chain, not when it is queued: a page picked from the
window just before, still queued behind the keys being sent, takes effect first and is seen (the
busy time counts the move whenever anything is queued ahead, an upper bound). Alignment starts by itself
once the mode selector is at ALIGN or NAV. It is refused while
an entry is open ("press Clear, then try again"). For a position update select Position first,
then press Hold: the manual's order, Hold then Position, does nothing in this aircraft. Automatic
waypoint loading is the NAVIGATION screen's AUTO BATCH (`L:INS_n_AUTO_BATCH_ENABLED`; turning it on
also fires `H:INS_n_RESUME_AUTOBATCH`, as the screen does; `L1011InsKeys.AutoBatchRpn`). The
button's label shows the state the INS reports ("Automatic waypoint loading: on", "off" or
"unknown") and the screen reader reads it when it changes, as it does the PMDG windows' buttons; the
app says nothing after the press (it said the new state itself first, and the screen reader then read
the label as well: a double, [CORE-7]). The window's selectors
are the INS panels' rows: each shows the position the aircraft reports and is written through its
row, behind the keys already chained, so a pick made while typed keys are still being sent never
lands between two presses (a refusal, such as "Display selector unavailable", is spoken when the
pick's turn comes).

The SimBrief route reaches the INS from the tablet's "Send to INS" (its OFP page; "Paper Flight
Bag" below): the captain's tablet loads INS 1, the first officer's INS 2, each time with SimBrief's
latest plan, and the tablet window reads back what the INS took. The aircraft turns that
unit's display selector to Waypoint and its automatic waypoint loading on, drops SID and STAR
waypoints unless the tablet setting "IMPORT SID/STAR WPTS" (Menu, Aircraft settings) is on, drops
TOC/TOD and the departure and arrival airports, and loads nine waypoints at a time into the slots,
so a short route can arrive with only two waypoints. A unit takes the waypoints only while it is
on: its mode selector at Standby or beyond, with power. Sent to a unit the window reads as off
("INS 1: off"), the selector and the automatic loading still change and the gauge records batch 1
of 1, but the slots of that send stay empty, so send again once the unit is on. The window shows
them as "Waypoint 1, KENNO: N 37 17.9, W 117 18.6" and
"Route: batch 1 of 1"; a typed waypoint's USER<k> name is left out, and the batch line is left out
once a power loss has emptied every slot (the gauge keeps the old batch numbers).

Remote: set all three auto/manual/remote selectors to Remote before typing waypoints, so an entry
typed into one unit reaches every unit. In Remote the leg window holds the pair being ranged
(Track change, two digits, Insert, then read Distance and time), so the "Leg: 7 to 8" line and the
"Leg 7 to 8" announcement are the ranging pair, not a flown leg.

What speaks ([L1011-15]): the INS lights (READY NAV, WARN and BATT for each unit, and the waypoint
ALERT for INS 1 only: the units light it together while they fly the same legs, and INS 1 feeds
the captain's HSI and the autopilot, INS 3 when the instrument source switch selects it) through
the warning-light gate; "INS 1 navigating" (`L1011InsAlignmentAnnouncer`, from
`L:INS_n_ALIGNMENT_STATUS`) only when a unit starts navigating by itself: its mode selector was
already at NAV while it aligned, so the status rested at 2 for one update and READY NAV lit for
that update only (about a second, below the lamp gate's settle time, so it is not spoken) before
the status went to 1; with the selector at ALIGN the READY NAV light stays on and is the
announcement, and the step to NAV is the pilot's own (the status rests at 2 for an update after the
turn, and a unit already known to be aligned keeps that 2 as aligned whatever the selector says; only
a status of 3 or more, a re-alignment, makes it aligning again). The countdown lands on
2.0000000000000053 for about a second before it is exactly 2 (READY NAV lights only at exactly 2;
measured in the INS view with a 40 ms sampler), and the variable cache ignores a change of 0.001 or
less, so the exact 2 never reaches the definition: a status within 1e-6 above a whole number counts
as that number (`L1011InsDisplay.ShownStatus`, for this call-out and the window's state line), while
16.67 is still 17. And "PMS climb", "PMS cruise", "PMS descent"
(`L1011PmsPhaseAnnouncer`, from `L:PMS_FLIGHT_PHASE`: 2 and 3 climb, 4 cruise, 5 descent, as the
PMS mode lights) when the aircraft changes the PMS mode. Each of these has its own Ctrl+M row.
While the window is open it also says a PMS's new page (the cursor goes to line 1) and an INS's new
leg (`L1011InsWindowAnnouncer`), and "Entry closed" when an entry closes. These three have Ctrl+M
rows of their own, on by default: "INS window leg changes", "INS window PMS page changes" and "INS
window entry closed" (the closing word only: what was typed is always read back, and a refused
value is always read). No variable stands behind them, so they are synthetic rows, as the A380's
ECAM row is (`L1011InsWindowCallouts`, `MonitorRowBuilder.BuildWithExtra`): their keys go into the
same disabled list and the window checks it before it speaks, at no batch slot and no on-request
definition. Muting the page row silences the title only; the cursor still goes to line 1.

## Paper Flight Bag (the tablet)

Input-mode Shift+T opens the captain's tablet and Ctrl+Shift+T the first officer's, in the shared
tablet window (`FbwEfbForm`, the window the PMDG and MD-11 tablets use, and the A300's on
`feat/inibuilds-a300`). Each seat's tablet is its own Coherent view, `iniEFBL1011_1` and
`iniEFBL1011_2` (`CoherentPmdgEfbClient.ForL1011`), read and driven by
`coherent-l1011-efb-agent.js`. As for the fleet's other tablets, MainForm owns one client and one
window per seat (`MainForm.ShowL1011EfbDialog`): the client is created on first use and kept until
the aircraft changes (`DisposeL1011Windows`, on a switch and on exit), it scrapes only while its
window is shown, and the window hides on close and is reused. Unlike the INS and autopilot readers,
the client keeps its view's one inspector socket while the window is hidden.

The tablet is a plain DOM app (msfs-sdk, not React). What the reader relies on:

- The eight tab buttons, the ground buttons and the flap buttons have no text: names come from
  tables in the reader, state from classes (`door-open`, `door-closed`, `door-transit`, `active`).
  The tabs are listed in the order they sit on the tablet (Menu, Ground, Load sheet, OFP, Takeoff
  performance, Landing performance, Charts, Enroute map); their DOM order differs.
- `el.click()` is the press, alone ([L1011-17]): no pointer or mouse prelude, which would start the
  drag sliders. Click-through or dimmed controls (`pointer-events: none`, opacity 0.35) are refused
  by the reader, because `click()` ignores pointer-events.
- A value typed into a field with the tablet's number pad (the load sheet, the takeoff conditions and
  the landing elevation) counts only when that keyboard submits it ([L1011-16]): input, change and
  blur leave the field showing a value the aircraft never took. The reader clicks the field (the
  number pad opens), sets the value, fires `input` and presses the pad's submit key
  (`#osk-num .osk-hide-num`, captioned LOAD on the load sheet). Fields without a keyboard (the
  landing weight, a plain number field; the descent calculator; the SimBrief Id, which saves on
  `keyup`) get input, keyup, change and blur.
- A setting's value is its label's `active` class, never the radio input's `checked` (the two
  disagree, [L1011-18]); clicking the label sets it and its `L:INI_*` follows within a second.
- A flight-engineer flow is collapsed while its `.event-list` lacks `expanded` (its steps are still
  laid out in a three-pixel strip), so steps are read only for an expanded flow.
- The chocks popup's buttons say what a press does ("INSTALL", "REMOVE", "OPEN", "CALL"); the reader
  says the state instead ("Chocks: installed").
- The OFP is one `pre` (about 1,440 lines, 57 KB for a real plan), passed through with its line
  breaks.
- The wrapper `#Electricity` around the tablet reads `state="off"` with the aircraft battery off while
  the tablet stays usable, so it is ignored.
- About 170 DOM changes a second happen with nothing changing for the pilot (hidden pages, and the
  ground buttons rewriting their classes five times a second), so the reader compares its own output
  to decide "unchanged", never a MutationObserver ([L1011-19]).
- The TOD timer's auto pause is a drag slider with no input behind it, offered as a text field,
  "Timer auto pause", holding the time the display shows. A typed time ("45", "2:30", "2h 30m", 0
  for none, up to 10 hours) is set by dragging the thumb and reading the display back until it shows
  that time: the scale is uneven. It is the reader's one drag ([L1011-17]); START TIMER is then an
  ordinary button.

Results the reader converts: takeoff EPR displays drop the leading 1 (".643" is 1.643, the same
convention as the PMS, whose gauge stores `epr / 1000 + 1`; the PMS lines get the 1 back the same way, "2: EPR 1.642"), and an empty or "-" result reads "not
calculated". The four flap speeds are read as the tablet shows them: V2 plus 10, 20, 60 and 70
knots, the manual's retraction schedule. Charts and the map are pictures and say so; the METAR
lookup on the charts page is offered. The tablet's own Power Off EFB sits in a header bar that is
hidden on every page, so it is not offered.

What speaks: the window speaks a page change and the first alert (the top-of-descent auto-pause, a
load or performance error, the Send to INS read-back below). Status lines the tablet rewrites (panel-state progress, the descent
calculator's result, the METAR answer, "auto pause is armed", the loading banner) are polite live
text, read while the window is open; the countdowns (the loading time remaining, the top of descent
timer and the distance to it) are updated in place but never read out by themselves, so a moving
number is not spoken every second. A pressed control whose label carries its new state (doors,
ground equipment, the chocks popup, the flows and their steps, the card toggles, the fuel manager's
switch) is read again after the press, the shell's `announceChange` opt-in ([MD11-26]) as the A300
reader uses it; nothing else is.

Send to INS (the OFP page) sends SimBrief's latest plan to INS 1 from the captain's tablet and to INS 2
from the first officer's. The press downloads the plan again, so what it sends is never the OFP the
tablet shows, and that OFP is not redrawn ([L1011-23]). The tablet writes the route's fixes to the
DataStore (`NAVIGRAPH_ARRAY`, or `NAVIGRAPH_ARRAY_2`) and fires `H:EFB_TO_INS_SENT` (or `_2`); a download
that fails (no SimBrief ID, no connection) sends nothing, and the tablet itself shows nothing either
way. "INS and PMS" says what the INS keeps of it and how the INS window shows it.

After a press from the window the reader reads the send back once the INS has loaded: two seconds after
the tablet's event, or after the last event of a unit in Remote taking the route too (one listener on
the tablet's page hears these events). "KLAS to KSFO sent to INS 1: 3
waypoints in 1 batch, first KENNO." Nothing of it comes from the OFP text: the destination is the
navlog's last fix, the origin the first point of the route overlay the press writes beside it (left
out, "Route to KSFO", when that shared key holds another tablet's plan), and the waypoints and batches
are what the INS keeps, nine to a batch. Units in Remote that take the route too are named ("sent to
INS 1, 2 and 3"). It adds "INS 2 is off and kept nothing: turn it on, then send again." for a unit that
emptied its list, the IMPORT SID/STAR WPTS setting when every fix was on the SID or STAR, and "This
tablet's OFP is an older plan: press Reload OFP to read the one sent." when the OFP shown is not the
plan sent. With no event within 15 seconds it says "Send to INS: nothing sent after 15 seconds" and
what to check; a later event is still read back. The read-back is an alert, spoken once, for 20
seconds; after that it is a line of text on the OFP page under Send to INS, which leaves out the older
OFP sentence once another OFP is shown (Reload OFP). The window reads only while
it is open: a read-back that comes while it is closed is spoken on reopening within those 20 seconds,
and is only that line after them.

The OFP page also says when its plan is not the route an INS holds: "This OFP differs from the route in
INS 1 (to KSFO). Reload OFP and Send to INS both use SimBrief's latest plan." An OFP shows a route when
it names the route's destination and its first and last named en-route fixes (no OFP layout is
parsed); a unit holds a route when its list in the DataStore (`IMPORTED_WAYPOINTS`, `_2`, `_3`) is what
the stored navlog gives. Each tablet keeps the OFP it last loaded, so the two can show different plans;
this line is how the older one shows itself. It is spoken when it appears, but not while a send is
being read back (the INS stores its list a second before the read-back is ready) and not once the
read-back has said so for that OFP; it is then a line of text.

## Troubleshooting

- Breaker window says "Breaker states unavailable", or Ctrl+P's first line stays "Autopilot
  windows not read yet": the Coherent debugger did not answer. A helper an EARLIER sim session
  launched (`simlink.exe`, or any add-on tool the sim starts) inherits that session's listener on
  port 19999 and swallows every connection: `netstat -ano | findstr 19999` shows two LISTENING
  owners, one of them a process that no longer exists. End the leftover helper (its parent is that
  dead process); starting it again by hand is safe.
- A control "does nothing": check the calc-path probe's warning (MobiFlight WASM module), then
  `debug.log` for the RPN sent.
