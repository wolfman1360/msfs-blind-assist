# First Officer: iniBuilds L-1011 TriStar — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/first-officer-l1011.md`, which Claude Code loads when it reads matching code. Background: [first-officer.md](../first-officer.md) (the TriStar paragraph) and [l1011.md](../l1011.md) (First Officer).

## FOL-1

- The TriStar First Officer never writes a control in a way of its own. Every write goes through the definition's First Officer entry, reached through `IL1011FoTransport` (`L1011DefinitionFoTransport`): `IniL1011Definition.FoSetAsync` for a map row, a lever or the stabilizer trim, and `FoSetAltimetersAsync` for the captain's, first officer's and standby altimeters in one string. `FoSetAsync` plans a map row through the panels' own write core (`PlanFor`, `ApplyPlan`) and sends a lever or the stabilizer trim from the panels' `L1011Levers` table, so a flow step writes a control exactly as a panel pick does: the click replay ([L1011-1]), the refusal of a toggle from an unknown position ([L1011-4]) and the engage paddle's CWS notch ([L1011-21]) included. `FoSetAltimetersAsync` plans nothing: it sends `L1011Levers.AllAltimetersRpn`, Ctrl+B's string, directly, sharing that table's range check and the `CanLand` gate. Never `HandleUIVariableSet`, the panels' entry, which speaks its own refusals, snaps a combo back, runs only on the UI thread and does not wait for a held press; and never a raw calculator string from the executor. Unlike the panels, the entry speaks nothing. It returns `L1011FoResult`: Sent, AlreadyThere, Refused with the reason the panel would have spoken, Unavailable when the definition is detached or gone or the calculator path cannot land, or UnknownKey. It completes only once the plan has run, a button's hold included, and it marshals onto the UI thread captured at `Attach`, so the executor may call it from any thread. The executor (`L1011FoActionExecutor`) runs every write behind one gate. It reads a readable key fresh before writing it, so the definition plans from a delivered value and never from an empty cache, then reads it back fresh until it shows the target or `VerifyTimeoutMs` passes; only then is the write done. A press, a spring switch or a knob holds no position to read (`IniL1011Definition.FoCanReadBack`) and is done once sent. A write not done is logged with its reason and never spoken by the executor: the flow says "Skipping", and a hand tick unticks with "Unable to complete". → [first-officer.md](../first-officer.md)

## FOL-2

- One voice. MainForm's UI echo ([CORE-8], [CORE-9]) covers only a panel pick, so a lever the First Officer moves (the parking brake, the flap handle, the ground-spoiler arm) would otherwise be spoken twice: the flow's own line, then the aircraft's lever call-out ("Parking brake set"). So the First Officer's hand-written writes (`FoSendCustom`) record their target in the definition's commanded state (`_commanded`, an `L1011CommandedState`) before sending, and `AnnounceLever` stays silent for a lever that reads its commanded position within the commanded hold. Nothing is recorded for a write that cannot land. A lever moved by anything else (the pilot, a hardware lever, the aircraft) is still spoken; a panel pick is not recorded, because the UI echo already keeps it quiet. A First Officer test that lights lamps (the standby power check) mutes the warning-light call-outs with `FoMuteLampSpeech` for its whole run: `StandbyCheckMuteMs` (20 s) from its start, re-armed for the same again right before the step 3 writes and right before the step 4 light round, because on the 1 Hz batch every fresh read waits for the next batch and the check can outlast one window, and a lamp change that begins after the window is spoken. A re-arm only ever moves the end later (`L1011LampGate.MuteUntil` keeps the later end); the mute's end is left to its time-out, never cut short, and a running annunciator light test is never shortened. The test speaks ONE verdict of its own through the announcer ([FO-26]): a sentence naming the first light that read wrong, such as "Standby power check: AC standby bus fail light came on", always; "Standby power check: pass" only while "Speak flow progress" is on. A write the test could not do is the flow's to say. A wrong light does not stop the check, so the aircraft still ends with the battery on and standby power armed. → [first-officer.md](../first-officer.md)

## FOL-3

- The TriStar's start cue is N3, so the First Officer reads its engines on N3 (`L1011_RO_N3_1` to `_3`, the engine gauges' `L:INI_ENGn_N3`), never the window's stock N2 feed: `L1011FoStateEvaluator` stores what `IFoEngine3N2Sink` delivers and no TriStar field reads it. An engine is running at N3 50 or above (idle is about 59). The engines are stopped when every N3 is below 5 AND every fuel and ignition switch reads off; a cold N3 gauge reads 1.4 to 1.9, never 0. The fuel and ignition switches are read on their rows (`TOGGLE_CUTOFF_ENG_n`, which read the stock fuel valves), never the L:var of that name, which reads 1 on a cold aircraft. An unread input is NaN, so the cold-and-dark guards (`FO_ENGINES_STOPPED`, [FO-25]) stop the flow rather than let it through. → [first-officer.md](../first-officer.md)
