# iniBuilds L-1011 TriStar — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/l1011.md`, which Claude Code loads when it reads matching code. Background: [l1011.md](../l1011.md).
The text is verbatim from CLAUDE.md on `feat/inibuilds-l1011` (then named `feature/l1011-panels`) as of `0ea00497`, moved here when that branch took the lean CLAUDE.md (#265); a trailing "→ doc" pointer is the original's.

## L1011-1

- Every write of a map-driven TriStar panel row or circuit breaker REPLAYS THE COCKPIT'S OWN CLICK: the L:var writes, H: events and K: events the control's mouse code performs for the chosen position, in order, as ONE `ExecuteCalculatorCodeUnique` string (`L1011WritePlan`). Never `SetLVar` and never a bare L:var write there: the TriStar's gauges re-read a switch only when its H: events fire, so the switch moves and nothing else does. The ONE deliberate exception is the hand-written rows in `L1011Levers`, which write what the aircraft itself reads: the flap handle `A:FLAPS HANDLE INDEX` (as the aircraft's own EFB does), the gear lever the stock `K:GEAR_DOWN`/`K:GEAR_UP` (intercepted by the HANDLING gauge) or `L:LEVER_LANDING_GEAR` 50 for Off, the speed brake `L:LEVER_SPOILERS` (both lever L:vars are polled by that gauge), and stock K: events for the spoiler arm, the parking brake and the typed values — still ONE `ExecuteCalculatorCodeUnique` string each, still never `SetLVar`. `IniL1011Definition.SetAutoBatch` is hand-written beside `L1011Levers`: it replays the NAVIGATION screen's own AUTO BATCH switch (`L:INS_n_AUTO_BATCH_ENABLED`, and `H:INS_n_RESUME_AUTOBATCH` when turning it on), a control that is not a map row. Every write, the exception included, is refused aloud ("{name} unavailable") when `CalcWriteCanLand` is false; a refused PANEL ROW or LEVER also asks for its value again so its combo snaps back to the aircraft's position (a breaker row is a list item that is not changed before sending, so it needs no re-read); a gear-lever write that was sent is re-read once after `L1011Levers.GearSettleMs`, because the lever's own gauge refuses "up" on the ground. → [l1011.md](../l1011.md)

## L1011-2

- `MSFSBlindAssist/Resources/l1011_control_map.json` is GENERATED by `tools/l1011-gen` from the aircraft's compiled cockpit behaviour and tooltips — never hand-edit it; after an iniBuilds update regenerate it and review with `diff_maps.py`. iniBuilds' files and any decoded copy of them stay out of the repo. → [l1011.md](../l1011.md)

## L1011-3

- `L1011PanelLayout` (and its `L1011LayoutRows.*.cs` row files) is the ONLY source of panel order — the manual's preflight flows — with the discriminator first in every name and a guard directly before its switch (pinned by `L1011PanelLayoutTests`). Its `SpokenWord` sentence-cases iniBuilds' upper-case position words but keeps single letters ("Loop A"), words with a digit and the letter-spoken abbreviations in its set ("TA/RA", "APU generator") in capitals. → [l1011.md](../l1011.md)

## L1011-4

- A transition carrying a TOGGLE K: event is REFUSED while the current position is unknown, and a just-commanded position is trusted for 2.5 s over the 1 Hz cache (`L1011CommandedState`): a toggle sent the wrong way inverts the switch and the system behind it. → [l1011.md](../l1011.md)

## L1011-5

- The warning-light flush runs in `OnContinuousBatchDelivered`, OUTSIDE MainForm's mute wrap, so it checks `L1011DisabledMonitorVariablesSet` itself; the lever call-outs speak inside `ProcessSimVarUpdate`, where the wrap applies. A context reset wipes the baselines and `Md11SeedGate` decides when the unchanged ones are seeded from the cache — never a wall clock. → [l1011.md](../l1011.md)

## L1011-6

- The 981 circuit breakers are NEVER data definitions (they would break the 1,000 budget): the breaker window reads them with one Coherent evaluation in `L1011_ENGINEER_PANEL`. Every breaker row carries its number ("ENG START PWR, breaker 741: in") — titles repeat ("INOP" ×68) — and the window re-filters ONLY on opening, a search or "pulled only" change and Refresh, never after a pull, a push or its confirmation read (the Ctrl+M monitor managers' rule), so the cursor never lands on another breaker. A position variable that two rows share rides the batch ONCE; the second row reads it on request. → [l1011.md](../l1011.md)

## L1011-7

- A typed autopilot value is written EXACTLY as the aircraft's own knob handler writes it (`L1011Afcs`, from L1011_AFCS.js and L1011_INSTRUMENTS.js, package 1.0.8): heading `K:HEADING_BUG_SET`; altitude `L:ALTITUDE_SETPOINT_0` then `H:AUTOPILOT_CAPTURE_UPDATE`, so the capture logic re-reads it; speed `L:INI_AT_TARGET`; vertical speed `L:INI_VS_PID_SETPOINT_2` then `H:AUTOPILOT_SWITCH_AFCS_VS_SEL`, what the vertical-speed wheel does; courses `K:VOR1_SET`/`K:VOR2_SET`. Each inside the knob's own clamp (speed 100 to 350, altitude 0 to 50,000 in 100 ft steps, vertical speed in 100 fpm steps). Never a stock autopilot variable or event the AFCS gauge does not read: the stock autopilot is disabled in systems.cfg and `A:AUTOPILOT ALTITUDE LOCK VAR` is not the selected altitude. The disconnect button fires `H:AUTOPILOT_AUTOPILOT_DISCONNECT`, the one event the yoke switch's click fires in either direction (verified live 2026-10-03). → [l1011.md](../l1011.md)

## L1011-8

- Two TriStar autopilot rules are enforced BEFORE anything is sent, because the aircraft otherwise undoes the press with nothing said: a pitch or lateral mode (`L1011AfcsModes.NeedFlightDirectorOrAutopilot`) is refused while both flight directors and both engage paddles are KNOWN off ("turn on a flight director or the autopilot first"; L1011_INS.js resets the button, seen live), and a vertical speed typed while VS mode is known off is refused ("turn vertical speed mode on first" — engaging the mode resets the target to the current vertical speed, seen live). An unknown position never refuses: the position is what MSFSBA just commanded, else the cache, else the last value delivered (`AfcsPosition`). → [l1011.md](../l1011.md)

## L1011-9

- The autopilot speaks only from variables the aircraft's gauges themselves use (`L1011AfcsModes`): the engage paddles, the mode buttons and the armed/captured flags (`ANN_LOC_ARM`, `ANN_LOC_ACTIVE`, `ANN_VOR_ACTIVE`, `ANN_ILS_ARM`, `ANN_ILS_ACTIVE`, `ANN_ALT_ARM`, `FLARE_ACTIVE`, `ROLLOUT_ACTIVE`) and the autothrottle's alpha mode (`INI_AOA_SPEED_MODE`, spoken both ways and never in the armed/captured list: `L1011AfcsModes.Flags` leaves it out), baseline-first, and MSFSBA's own press is silent only while the switch sits where it was put — the PMDG windows' value-matched echo (`PMDGAutopilotRowBinder`): within `L1011CommandedState.HoldMs`, a delivered value that differs from the commanded one is the aircraft moving the switch and is spoken, and a value box button or toggle key reads its own result back, so the call-out stays quiet for that key until the read-back has spoken (`_readBackPending`). A flag speaks only at the value its words name (`FLARE_ACTIVE` reads 99 while armed). Package 1.0.8 has NO autopilot- or autothrottle-disconnect warning variable: never announce the gauge's `AFCS_CPT_*` 0/50/100 annunciator drums, whose legends the code does not name, nor a lamp whose meaning is unconfirmed (the glareshield ALERT lights, `LX_MIP_DUAL_AVL`). → [l1011.md](../l1011.md)

## L1011-10

- The Ctrl+P window's lines come from the read-only `coherent-l1011-afcs-agent.js` (`#screen_1..8` and `#customElectricity` in `L1011_AFCS`), formatted in C# by `L1011AfcsWindows`, which drops the gauge's "X" blank-digit padding — the agent returns the windows exactly as drawn. Pinned by `tools/l1011-display-test` (jsdom, CI) and `L1011AfcsWindowsTests`. The window is the shared `PMDGAutopilotWindow`, which HIDES on close and is reused, so the definition starts the reader when the window becomes visible and disposes it when it is hidden or disposed (`SetAfcsReader`, on `VisibleChanged` and `Disposed`), and the definition's `Dispose` stops it too: the view allows one inspector socket, and a reader kept for a hidden window would hold it for the session. → [l1011.md](../l1011.md)

## L1011-11

- The TriStar's input-mode autoflight windows follow the A300's ([A300-17], [A300-18] on that branch): `L1011AutoflightWindows` lists what each window carries, each control in one window only (the value boxes their axis's mode buttons; Ctrl+P the flight directors, turbulence, the radio navigation and approach modes, the disconnects, TO/GA and the engage paddles); every label is the panel row's name; every press goes through the row's write path (`HandleUIVariableSet`, `ToggleControl`), so the refusals and the commanded hold match the panels. Every value box, Ctrl+B's included, is one `ValueInputForm` type and `ShowTrackedWindow` keys on the type, so `ShowValueBox` closes an open box with another title first (`ReplacesOpenBox`); never show a TriStar value box through `ShowTrackedWindow` alone. A value box button and a toggle key read their result back FRESH after `ToggleReadBackMs` (the aircraft turns some presses straight back, and the box's own echo reads the 1 Hz cache), so the box's echo is off (`SuppressStateAnnounce`); the read-back is queued (`Announce`), never interrupting, so the call-outs a press sets off are heard first; Ctrl+P says nothing on a press. A label, a combo and a status line show the position the aircraft REPORTS (the cache, else the last delivery: `ReportedPosition`), never the commanded hold, which decides only which way a toggle goes and whether a refusal applies (`AfcsPosition`; the PMDG windows' rule: a label must never say On for a switch that has not moved). → [l1011.md](../l1011.md)

## L1011-12

- `ANN_VOR_ACTIVE` is the VOR (or back-course) capture ONLY while the VOR or back-course mode button is on. L1011_INS.js (package 1.0.8) writes it from its radio-navigation routine, which runs with every mode off: with no localizer, ILS or back-course mode selected, its VOR branch checks only that a navaid is received (`NAV HAS NAV` and a non-zero to/from) and sets the flag to 1, and with no signal it returns early without clearing it. So the flag read 1 at the gate with NAV 1 tuned and VOR mode off, and went straight back to 1 when cleared by hand (measured 2026-10-15), and the Ctrl+P list read "VOR captured" before this rule. `L1011AfcsModes.FlagModeOn` gates it on `SWITCH_AFCS_VOR` or `SWITCH_AFCS_BC` being KNOWN on; `L1011AutopilotStatus` lists the flag only then, the Autopilot panel's status display shows it "on" only then (`IniL1011Definition.TryGetDisplayOverride`; it read "VOR captured: on" with VOR mode off before), and `L1011AfcsAnnouncer` speaks the gated value, so a navaid tuned with VOR mode off is silent and VOR mode coming on over one speaks "VOR on" then "VOR captured" (the capture still speaks when MSFSBA pressed the button: it is the aircraft's). Pinned by `L1011AfcsModesTests`, `L1011AutoflightWindowsTests` and `IniL1011AutopilotBehaviourTests` (the panel's list by `The_autopilot_panels_status_list_shows_a_vor_received_with_vor_mode_off_as_off`). → [l1011.md](../l1011.md)

## L1011-13

- The INS window reads ONE INS view at a time through the read-only `coherent-l1011-ins-agent.js`: `L1011_INS_1` holds INS 1 and the CAPTAIN's PMS, `L1011_INS_2` INS 2 and the FIRST OFFICER's PMS, `L1011_INS_3` INS 3, whose PMS copy is inert (L1011_INS.js compares PMS keys with `insIndex - 1` and starts the PMS timer only for views 1 and 2), so a PMS is never read from view 3. It reads the window SPANS (`#left_0..5`, `#right_0..6`, `#tk_0..1`; the digit pictures lag up to 200 ms), the decimal points from `#dot_5`/`#dot_6`, the page from `L:INS_n_ROTARY_MODE` (the dots cannot identify it: modes 0 and 7, and 3, 4 and 8, light the same dots), every lamp from its L:var (there are no lamp elements), and the waypoints from the gauge's own `gpsPoints[1..9]`, never the `INS_WAYPOINTS` DataStore table, which read empty until the unit had power and is rewritten only once a second (seen live, 2026-10-03). `L1011InsForm` hides on close and is reused, so the reader follows its visibility, not its life: it holds the view's one inspector socket only while the window is shown, and a unit switch to another view moves it once the unit combo has rested for 300 ms. Pinned by `tools/l1011-display-test/ins.test.js` (jsdom, CI) and `L1011InsScrapeTests`. → [l1011.md](../l1011.md)

## L1011-14

- Every INS and PMS key goes through ONE chain in the definition (`IniL1011Definition.PressKeys`, `Chain`), so two quick presses never interleave: each key is the cockpit's own click (the map control's press effects, then its release effects: `L1011WritePlan.ForPress`, [L1011-1]), and a RUN of keys (typed text, one key, the present-position sequence, INSERT; the PMS keys too) goes out as ONE `ExecuteCalculatorCodeUnique` string with every click back to back and no wait between them (`L1011InsKeys.ClickRpn`, `RunSteps`). Measured live 2026-10-15: the INS takes several keys in one string, in order ("N" then "4 3 4" in one string read "  434N"; "0 9 INSERT" in one string stored the latitude exactly as key by key; L1011_INS.js has no debounce), which replaced a 60 ms hold and a 40 ms gap per key (about 1.5 s for a position). A run past `L1011InsKeys.MaxRunLength` (900 characters: the MobiFlight command channel holds 1,024, terminator included, and the unique prefix adds `{seq} 0 * `) is cut into consecutive strings between keys, NEVER inside one, with `RunGapMs` (50 ms) after each string. A selector move from the window (`SetInsSelector`) waits behind every key already chained, through the same chain and still the panel row's own write path ([L1011-11]), so it never lands between two presses. Typed text holding a character the unit has no key for sends NOTHING: INSERT with too few digits is silently ignored by the gauge, so half a position would stay open, and a stray key could start another entry. "Enter present position" turns the display selector (the manual's "Display selector switch", `L:INS_n_ROTARY_MODE`) to POSITION first, because on any other page the N/S/E/W keys start no entry (L1011_INS.js); the present-position keys typed this way aligned INS 1 live (2026-10-03). `EnterPresentPosition` (the selector move, `SelectorSettleMs`, then the 15 keys as one 744-character string) and `SetAutoBatch` (one calculator write, `L1011InsKeys.AutoBatchRpn`) chain through the same `Chain` as `PressKeys`, so each waits for everything chained before it. Whether `EnterPresentPosition` moves the selector is decided when its run reaches its turn (`ChainBuilt`), NOT when it is queued: a page picked from the window just before it (`SetInsSelector`, queued behind the keys) records its position only when it runs, so a queue-time decision saw the old page, chained no move and keyed the position onto the picked page; `KeysBusyForMs` counts the move whenever anything is queued ahead or the selector is not known at POSITION, an upper bound. The window holds its read-back of what was typed until the chain has run (`KeysBusyForMs`: the sum of the waits in the chained steps). Pinned by `IniL1011InsBehaviourTests` and `L1011InsKeysTests`: the one-string runs and their exact press and release order by `A_typed_run_is_one_string_with_each_keys_press_then_release_in_order`, `Insert_is_the_last_click_of_the_same_string` and `The_pms_keys_follow_the_same_path`; the cut between keys by `A_run_longer_than_the_limit_splits_between_keys_with_a_gap_after_each_string` and the `L1011InsKeysTests` packing tests; the selector waiting for the keys by `A_selector_pick_waits_for_the_keys_queued_before_it`; the move decided at the run's turn by `Enter_present_position_decides_the_selector_move_when_its_turn_comes` (and no move when the selector is already there by `Enter_present_position_behind_queued_keys_moves_nothing_when_the_selector_is_at_position`); "turns the display selector to POSITION first" by `The_present_position_entry_turns_the_selector_to_position_then_keys_the_position` (the selector at another page: the move, a 400 ms settle, the position string, `KeysBusyForMs` 450) and, with the selector already at POSITION and no settle chained, by `The_present_position_entry_chains_no_settle_when_the_selector_is_already_at_position`. → [l1011.md](../l1011.md)

## L1011-15

- "INS n navigating" speaks ONLY when a unit starts navigating by itself: its mode selector (MSU) was already at NAV while it aligned, so the status went from aligning to 1 on its own (L1011_INS.js; live, 2026-10-15: with the MSU at NAV the status rests at 2 for one 1 Hz update, about a second, and READY NAV lights for that one update before the status goes to 1; the flash is below `L1011LampGate.SettleMs`, 1,200 ms, so the warning-light gate never speaks it, pinned by the lamp gate test in `IniL1011InsDefinitionTests`). With the MSU at ALIGN the READY NAV lamp stays on and is the announcement (the warning-light gate) and the step to navigating is the pilot turning the knob, never spoken: the status rests at 2 for one update after the turn, so `L1011InsAlignmentAnnouncer` keeps a unit it KNOWS is aligned aligned at a 2 whatever the MSU reports, and only a status of 3 or more (a re-alignment) makes it aligning again (the first version re-read that 2 with the MSU at NAV as aligning and spoke "INS 1 navigating" over the pilot's own turn, live 2026-10-16; pinned by `Turning_the_knob_to_nav_while_the_status_still_rests_at_two_stays_silent` and, through the commanded MSU, `Turning_the_mode_selector_from_align_to_nav_in_the_app_does_not_say_navigating`). The status the definition receives is not always the exact 2: the countdown lands on 2.0000000000000053 for about a second first (READY NAV lights only at exactly 2; measured with a 40 ms sampler in the INS view, 2026-10-16) and the variable cache drops the exact 2 as a change of 0.001 or less (`SimConnectManager.ChangeTolerance`, `IsValueChange`), so `L1011InsDisplay.ShownStatus` counts a status within 1e-6 above a whole number as that number, in the announcer and in the window's state line (16.67 stays 17); never round a status with a bare `Math.Ceiling`. Pinned by `The_live_countdown_to_aligned_then_the_pilots_turn_to_nav_is_silent`, `The_live_countdown_with_the_msu_at_nav_throughout_speaks_navigating_once`, `Turning_the_mode_selector_to_nav_after_the_live_countdown_does_not_say_navigating` and `A_status_a_hair_above_two_reads_as_aligned`. The PMS call-outs follow the PMS mode LIGHTS (`L1011PmsPhaseAnnouncer`: `L:PMS_FLIGHT_PHASE` 2 and 3 climb, 4 cruise, 5 descent; the ground, 1 and 7, and a go-around, 9, light none and are silent). Only INS 1's waypoint ALERT lamp is announced: the three units light it together while they fly the same legs (each computes `INS_n_ALERT_INDEX` from its own TO waypoint and ground speed), and INS 1 feeds the captain's HSI and the autopilot (INS 3 when the instrument source switch selects it), so its alert is the one the flying pilot needs; a pilot navigating on INS 2 or 3 alone hears none. Pinned by `L1011InsAnnouncersTests` and `IniL1011InsBehaviourTests`. → [l1011.md](../l1011.md)

## L1011-16

- A typed value in a tablet field that carries `data-keyboard` (the load sheet's fuel, cargo and passenger fields, the three takeoff conditions and the landing elevation; the landing weight is a plain `type=number` field without it) commits ONLY through the tablet's own keyboard. `coherent-l1011-efb-agent.js` (`setValue`, its `typeInto`) clicks the field (the tablet opens its number pad, `#osk-num`), focuses it, sets the value through the native setter, fires a bubbling `input` and clicks the pad's submit key (`#osk-num .osk-hide-num`, captioned LOAD on the load sheet), then lets the field go. The tablet applies a value only from that key; the field's own `oninput` handler only filters the characters. Measured live 2026-10-03 (package 1.0.8): focus, value, `input`, `change` and `blur` left tank 1 at 35,427 lb with the field still showing the typed text; through the pad, `A:FUELSYSTEM TANK WEIGHT:3` read 35,501 lb for 35.5, the total followed and the pad closed. A field with no `data-keyboard` (the landing weight; the descent calculator's fields; the SimBrief Id, which saves on `keyup`) takes `input`, `keyup`, `change` and `blur`. Never harmonise this with the A300 tablet's reader, where setting the value and firing input, change, keyup and blur is enough and a field is never focused: here that path leaves the aircraft unchanged. Pinned by `tools/l1011-display-test/efb.test.js` ("a load sheet value is submitted through the tablet keyboard, and the field is let go", "with no keyboard open a field takes input, keyup, change and blur"). → [l1011.md](../l1011.md)

## L1011-17

- A tablet press is `el.click()` and nothing else. The Paper Flight Bag is msfs-sdk FSComponent markup with plain `addEventListener` handlers, so `click()` reaches them on a `<button>`, a `<div>` button, a `<label>` and an `<li>`; a pointer or mouse prelude (the MD-11 tablet's sequence, [MD11-13], and the A300 tablet's pointerdown, mousedown, pointerup, mouseup, click) would start the tablet's custom drag sliders, which listen for `mousedown`. Because `click()` ignores CSS pointer-events, the reader refuses (returns false and sends nothing) a control that is `disabled`, whose computed `pointer-events` is `none`, or whose own inline opacity is 0.5 or less: that is how the tablet makes a control unavailable (`#ls-step2-btn`, `#ls-start-btn` and `#ls-timed-stop-btn` carry `opacity: 0.35; pointer-events: none`). The top-of-descent overlay is `pointer-events: none` while its UNPAUSE button is `auto`, so the decision is the control's own computed style, never an ancestor walk. Pinned by `tools/l1011-display-test/efb.test.js` ("a press is one click and nothing else; an unknown or click-through control is refused", "kilograms, and the timed loading controls once TIMED is chosen", "the top-of-descent pause comes first as an alert, and its unpause button still works"). The one exception is the TOD timer's auto pause, a thumb dragged along a track with no input behind it: `setTimer` sends a mousedown on the thumb and a mousemove and mouseup on the document, which moved it on the live tablet, and because its scale is uneven (live: "06m" at a tenth of the track, "1h 13m" at three tenths, "10h 00m" at the end) it searches the position by reading the display back until it shows the typed time; a typed time it cannot hold (more than 10 hours, not a time) leaves the slider alone. Live, 1:30, 45, 2h 5m and 0 read "1h 30m", "45m", "2h 05m" and "No timer". Pinned by "a typed time drags the timer slider until the display reads it" and "a time the timer cannot hold is refused and the slider is left alone". → [l1011.md](../l1011.md)

## L1011-18

- A tablet setting (the Aircraft settings pane's groups, the audio voices, the throttle calibration choices) is a Bootstrap radio group, and its value is its LABEL's `active` class, never the radio input's `checked`: the two disagree on the live tablet (2026-10-03: the Weight Units label "IMPERIAL - LBs" active with its input unchecked, and another group with both set). A setting is changed by a click on the option's label (`label[for]`): live, the label took `active`, the input `checked`, and the backing `L:INI_*` followed within a second (`L:INI_mapDisplay_SCREEN` 0 to 1 and back). The PMDG tablet's unit toggles are the opposite case ([PEFB-7]: the live `el.checked`), so do not carry that rule over. The Third party pane's Streamer Mode switch is a `form-switch` checkbox, read from its `checked`. Pinned by `tools/l1011-display-test/efb.test.js` ("aircraft settings: one dropdown per visible setting, its value from the active label", with the input's `checked` set against the label). → [l1011.md](../l1011.md)

## L1011-19

- The tablet reader answers `{"ok":true,"unchanged":true}` only when the scrape it just produced is identical to the last one it returned, never from a MutationObserver gate (the MD-11 reader's): measured live 2026-10-03, about 170 mutation records a second arrive with the OFP showing, all inside hidden pages (`page-options` child lists, `page-test-basic` classes), and with the ground page showing each door button's class is rewritten about five times a second with no net change, so a mutation gate would never close; and a property write (SYNC, a SimBrief import, timed loading filling a field) raises no mutation record at all, so a mutation gate would also miss real changes. A re-injected reader answers in full first. The reader also ignores the `#Electricity` wrapper's `state`: the wrapper around the tablet read `state="off"` with the aircraft battery off while the tablet stayed displayed and a tab press still changed the page, so reporting the tablet unpowered from it would hide a working tablet. Pinned by `tools/l1011-display-test/efb.test.js` ("\"unchanged\" only while nothing the pilot reads has changed, values included", "a tablet whose power wrapper says off is still read"). → [l1011.md](../l1011.md)

## L1011-20

- The tablet fixtures (`tools/l1011-display-test/fixtures/efb-*.html`) are captured with `efb-capture.js`, never `stamp.js` (which returns the whole body): it stamps `data-vis="1"` from the live computed style, clones the tablet, keeps the tab bar, the pause overlay, the keyboard shell and the shown page (on the Menu, only the sidebar and the shown pane), and removes iniBuilds' inline handlers, decorative images, coordinates, every field value, the Navigraph sign-in code and the logged-in Navigraph user name, the charts page's airport shortcuts (their text and `data-airport`) and its METAR answer, and the OFP text, replaced by a two-line stand-in. So no SimBrief ID, flight plan, airport or account reaches the repository (`efb-flows.html` was trimmed by hand afterwards to three flows). Pinned by `tools/l1011-display-test/efb.test.js` ("the capture tool keeps no personal data"). The tablet client keeps its view's socket until the aircraft changes, so a capture needs MSFSBA closed or another aircraft loaded. → [l1011.md](../l1011.md)

## L1011-21

- An autopilot engage paddle (`SWITCH_AFCS_AP_A`, `SWITCH_AFCS_AP_B`: 0 Command, 1 CWS, 2 Off) going to Command from Off, or from a position not known, goes to CWS first, rests `L1011WritePlan.PaddleNotchMs` (500 ms) and then goes to Command, each move the cockpit's own click ([L1011-1]). L1011_INS.js sets `L:AUTOPILOT_ACTIVE_MODE` from both paddles on any `AUTOPILOT_*` event and, 50 ms later, runs the moved paddle's routine for that mode: Off turns `L:INI_PITCH_PID_STATE` and `L:INI_ROLL_PID_STATE` off, CWS turns them on and holds the attitude, and Command only re-fires the selected mode buttons' events and leaves the loops as they are. Measured live on the ground: a paddle sent straight from Off to Command read Command with both loops off (the aircraft flies nothing while the Command light is on); Off, then CWS (loops on), then Command read Command with both loops on; CWS and Command in one string, or in two strings sent back to back, read Command with the loops off, because the routine reads the paddles only after its 50 ms timer. The rest outlasts a frame for the event, the timer and a frame to run, twice over at 10 frames a second (the sim measured 25 ms a frame at the time). Every other paddle move is one step: from CWS to Command the loops are already on. The CWS notch is recorded as a position passed through (`L1011Plan.Via`, `L1011CommandedState.IsOwn`), so a delivery that catches the paddle at CWS on its way is MSFSBA's own and is not spoken. ## L1011-22

- The APU start button's press is `L:SWITCH_APU_START` set to 1, then `H:APU`, in one calculator string, held for `L1011WritePlan.PolledButtonHoldMs` (2,000 ms) before the release writes 0. ON" sets the switch and then sends `H:APU` (with the master switch, the APU bleed, the bearing and the engine 2 tank valve), and the master switch's own click sends `H:APU` too. ## L1011-23

- The tablet's SEND TO INS (`analyzeSimbriefRouteText` in the tablet script, package 1.0.8, read from the code with its strings decoded) calls `getLastFlightPlan()`, which DOWNLOADS SimBrief's latest plan for the stored SimBrief ID every time: it never sends the OFP the tablet shows, and it does not redraw that OFP either (only Reload OFP and the page's first load do). So a tablet still showing an older OFP sends the latest plan, and the risk is reading a stale OFP, not loading a stale route. The handler has no error handling: a failed download (no ID, no connection) writes nothing and fires nothing. On success it writes, in one synchronous run, the navlog fixes to the DataStore (`NAVIGRAPH_ARRAY` from the captain's tablet, `NAVIGRAPH_ARRAY_2` from the first officer's: the first SID fix to the destination airport, type `apt`, never the origin) and the shared `NAVIGRAPH_ROUTE_OVERLAY` (the origin, named by its ICAO code, then those fixes, skipping a fix at the same place as the one before), then fires `H:EFB_TO_INS_SENT` or `_2`. One second later INS n filters the fixes (`simbriefToArray`: the airports at either end, TOC and TOD, and the SID and STAR fixes unless `L:INI_SIDSTAR_IMPORT`) and writes its list to `IMPORTED_WAYPOINTS(_n)` ("SB01 - KENNO/N3717.9/W11718.6" a line, idents cut to five); a unit in Remote passes the route to the other Remote units with their own event; a unit whose mode selector is at Off, or without power, runs `resetNavigationWaypoints` every update, which empties its slots and that key. So `coherent-l1011-efb-agent.js` arms on the pilot's own press of the button (`clickElement`, `armSend`), hears the seat's event (and a Remote unit's after it; an event name is looked up as an OWN property, since `constructor` would match any object) through ONE `Coherent.on('OnInteractionEvent')` listener per page (a reinstalled reader clears the one before it, `listen`; seen live 2026-10-16: a listener in a TriStar view hears an H: event fired from any view), and 2 s after the last such event (a unit loads a second after its own) reads the DataStore back (`readBack`): the destination from the navlog, the origin from the overlay only when the overlay's fixes are this navlog's in order (another tablet loading a plan rewrites that key), the waypoints and batches from the INS's own filter, and "off" for a unit whose list is empty. No event within 15 s says nothing was sent. The OFP text is only ever SEARCHED, never parsed: an OFP shows a navlog when it names its destination and its first and last named en-route fixes (`ofpShows`), which held on the live tablet (lat/long points and a STAR pseudo point are written differently, so they are not looked for); a tablet's OFP that does not show the route an INS holds (`heldRoutes`: a unit's list paired with the navlog that makes it) is said once, and not while a send is pending: in the first live test (2026-10-16, a KBOS to CYUL plan sent from tablets still showing an older OFP) the INS stored its list a second before the read-back was ready, so the page warning spoke first and the read-back then said the same. The kept read-back line drops its older-OFP sentence once another OFP is shown (`sendText`), since after Reload OFP it told the pilot to reload.
